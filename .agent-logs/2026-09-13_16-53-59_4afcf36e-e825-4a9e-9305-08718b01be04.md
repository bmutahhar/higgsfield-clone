## Approach

**Not Tooltip, and no new dependency.** Two reasons to diverge from the shadcn suggestion — say the word and I'll do it your way:

1. The live component is a `NavigationMenu`, not a Tooltip. A tooltip is `role="tooltip"`; it can't legitimately contain 26 links, and screen readers won't navigate into one. This content is a menu of anchors.
2. [CLAUDE.md](CLAUDE.md) says open/hover state is CSS, never React state — and the repo currently has zero Radix/shadcn deps. `group-hover:` + `group-focus-within:` does this without a state machine, exactly like the existing [tooltip.tsx](src/components/overlays/tooltip.tsx).

**The one real constraint:** the nav row is `overflow-x-auto` (it scrolls horizontally rather than collapsing), which clips absolutely-positioned children. So the panel is `position: fixed` — escaping the scroller without a portal or any measurement. I checked the ancestor chain: no transforms, which is the only thing that would break `fixed`.

Each menu item becomes a wrapper `div.group/menu` spanning the **full header height** — so the pointer never crosses a dead zone travelling from the link down to the panel — containing the existing `<Link>` plus the panel. The panel sits at `fixed left-4`, matching the live site's x=16 (the header's own `px-4` inset), and tracks the header's shrink through the `data-compact` group attribute that's already there: `top-13 group-data-compact:top-9`. Width `min(915px, 100vw-2rem)`, `max-h-[800px]`, scrolls internally — the live panel's exact measurements.

**Keyboard tradeoff:** opening on `focus-within` means tabbing to *Image* expands 26 links you then tab through to reach *Video*. Radix avoids that with arrow-key roving; pure CSS can't. The alternative — not opening on focus — makes the content unreachable by keyboard, which is worse. I'd take the long tab order.

## The component

One new `src/components/overlays/coming-soon.tsx` that owns the whole inert-entry treatment — the dimmed `<span aria-disabled>`, the bubble, and the accessible text. Call sites shrink from a hand-rolled span to:

```tsx
<ComingSoon side="under-header" className={cn(NAV_LINK, "cursor-default text-[#A8A8A8]/45")}>
  {content}
</ComingSoon>
```

Screen readers get a visually-hidden "— coming soon" appended inside the trigger, and the bubble is `aria-hidden`. That beats `aria-describedby` here because it needs no id plumbing, and it replaces the `title` attribute these currently rely on.

## Why not just wrap things in the existing `Tooltip`

I measured it in the running app: in the header row a `relative`-wrapped tooltip lands in exactly the right place and is **invisible**. The nav is `overflow-x-auto`, which makes `overflow-y` compute to `auto` as well, so it clips — the hit test comes back as the page content behind it.

The fix, verified across four items: mix the two anchors. `absolute top-full` with **no** `left`. `top` resolves against the nearest positioned ancestor — the header, already `relative` from the hover-menu work — so the bubble clears the clip and sits at the header's bottom edge. `left` stays `auto`, which falls back to the *static position*: for a flex child that's the trigger's own content-box corner. So x tracks each item (measured 247 / 302 / 351 / 727 under items at 239 / 294 / 343 / 719), y is constant at header-bottom + 8, and it follows the compact header for free. No JS, no per-item values, one class string.

That trick is header-specific, so `side` has three values:

| Surface | `side` | Why |
|---|---|---|
| Header row, 14 entries | `under-header` | the anchored variant above |
| Hover-menu Features rows, 28 | `right` | the panel is its own scroller; the left column ends at ~447 in an 880px panel, so a right-side bubble stays inside it. The right column is all live models — no tooltips there |
| Mobile tab bar, 3 tabs | `top` | bar sits at the bottom, no clipping ancestor |
| Auth dialog Terms / Privacy | `top` | inside the dialog |
